# hmm-3end

Exploring mRNA 3′-end sequence architecture and poly(A)-associated signals, working toward a Hidden Markov Model (HMM) for 3′-end identification.

## Overview

This repo covers the full project: raw Nanopore reads through candidate extraction, mapping, and eventually HMM modeling. The target model follows the design in Hajarnavis, Korf & Durbin (2004), *A probabilistic model of 3′ end formation in C. elegans*.

Right now the focus is finding candidate 3′-end reads. Long-read library prep leaves a poly(A) or poly(T) run next to a known adapter (CRTA, from SQK-PCB114.24). We use that pattern to pull out reads worth keeping, then trim them down to the transcript sequence just upstream of the tail.

Two methods are being tried in parallel:

- `preliminaryA.py`, a regex scan for the run + adapter pattern
- `blastA.py`, the same idea but using BLAST to find the pattern instead

### data/

Test datasets and generated files. Main test set is `data/1k.fastq.gz`. `data/hooks.fa` holds the poly(A)/poly(T) hook sequences used by `blastA.py`, generated by `hookprep.py` rather than written by hand.

### scripts/

```
preliminaryA.py   regex-based extraction
blastA.py         BLAST-based extraction
hookprep.py       builds hook sequences for blastA.py
fastq2fasta.py    converts fastq to fasta for blastA.py
readlen.py        read length stats
mrnalen.py        mRNA length stats
```

`preliminaryA.py` looks for a long A or T run followed by the adapter, reverse-complements poly(T) hits so everything ends up in the same orientation, and keeps the ~100 nt of transcript sequence before the tail. Reads are labeled `keep`, `both`, `neither`, or `short` depending on what was found.

`blastA.py` does the same job a different way: it builds a BLAST database from the reads and searches it with hook sequences (a short A/T run plus adapter prefix) instead of a regex. The goal is to compare both approaches on the same data and see which one holds up better once things scale.

`draft/` holds earlier scripts kept for history, not in active use.

### notebooks/

`qcfastq.ipynb` has the read-length QC and the parameter checks behind `preliminaryA.py`, including confirming the adapter shows up in both orientations and testing how much of the adapter is actually needed.

### envs/

`env1.yml` is the conda environment for this repo.

### shell/

Scripts for running extraction across many FASTQ files at once.

### dummy_3end.json

A placeholder HMM structure. Not the real model yet, just a sketch of the states it should eventually have.

## blastA.py notes

`blastA.py` builds a BLAST database from the reads (`formatdb`) and searches
it with poly(A)/poly(T) hook sequences (`data/hooks.fa`, generated by
`hookprep.py`) using `blastall -p blastn`. Getting it to actually return
correct hits took three rounds of debugging, and each one taught me
something about how BLAST works that I didn't know going in.

**DUST filtering.** My first run gave zero hits, no matter what e-value I
tried. Took me a while to figure out why: BLAST filters out low-complexity
regions from the query by default, and my hooks are mostly a homopolymer
run (15 nt of A or T out of a 35 nt query). The filter was masking out the
exact part of the hook I actually care about, so there was nothing left to
align. I fixed this with `-F F` to turn the filter off. I didn't know BLAST
did this kind of filtering automatically until I hit it.

**Scoring scheme.** Once I turned off DUST, I still got zero hits. I had
copied a scoring scheme (`-r 1 -q -1 -G 2 -E 1`) from a BLAST script in
another project, without thinking about whether it fit my case. I learned
that scheme was tuned for long sequence-vs-sequence alignments, and it's
too weak to make a 35 nt query pass a strict e-value even with a perfect
match. Once I dropped the custom scoring and let BLAST use its defaults,
hits showed up. This was a good lesson that a scoring scheme isn't
universal, it has to match the kind of alignment I'm actually running.

**Strand search.** After fixing the two issues above, I was getting hits,
but almost every read was showing up under both `polyA_hook` and
`polyT_hook`, which didn't make sense since those two are supposed to be
different orientations. I dug into the actual coordinates in the output
and noticed the start/end positions were flipped for a lot of hits, which
means BLAST was matching the reverse strand. I learned `blastn` searches
both strands of the query by default. Since my two hooks are already each
other's reverse complement, leaving both strands on meant `polyA_hook` was
also quietly searching for `polyT_hook`'s pattern, and vice versa. That's
why almost everything looked ambiguous. I fixed it with `-S 1`, which
restricts the search to the plus strand only. Before this fix: 502 hits,
250 unique reads. After: 501 hits, 498 unique reads.

Command `blastA.py` runs under the hood, after all three fixes:

```bash
blastall -p blastn -d build/reads.fa -i data/hooks.fa -F F -S 1 -e 1e-10 -m 8
```

### First result (1k.fastq.gz)

- 501 hits total, 498 unique reads with at least one hit
- 2 reads hit by both hooks, meaning genuinely ambiguous orientation
- one of those two, `c3e3d120-3869-4a45-98fa-7eb281b5ed2b`, is a read I
  had already flagged by hand during the regex/notebook work as having
  both a PolyA and a PolyT junction. Seeing BLAST land on the same read
  independently was a good sanity check that both methods are picking up
  on something real
- I haven't compared this against `preliminaryA.py`'s numbers yet, that's
  the next thing to do
