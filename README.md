# hmm-3end

Exploring mRNA 3′-end sequence architecture and poly(A)-associated signals, working toward a Hidden Markov Model (HMM) for 3′-end identification.

## Overview

This repo covers the full project: raw Nanopore reads through candidate extraction, mapping, and eventually HMM modeling. The target model follows the design in Hajarnavis, Korf & Durbin (2004), *A probabilistic model of 3′ end formation in C. elegans*.

Right now the focus is finding candidate 3′-end reads. Long-read library prep leaves a poly(A) or poly(T) run next to a known adapter (CRTA, from SQK-PCB114.24). We use that pattern to pull out reads worth keeping, then trim them down to the transcript sequence just upstream of the tail.

Two methods are being tried in parallel:

- `preliminaryA.py`, a regex scan for the run + adapter pattern
- `blastA.py`, the same idea but using BLAST to find the pattern instead

### data/

Test datasets and generated files. Main test set is `data/1k.fastq.gz`. `data/hooks.fa` holds the poly(A)/poly(T) hook sequences used by `blastA.py`, generated by `hookprep.py` rather than written by hand.

### scripts/

```
preliminaryA.py   regex-based extraction
blastA.py         BLAST-based extraction
hookprep.py       builds hook sequences for blastA.py
fastq2fasta.py    converts fastq to fasta for blastA.py
readlen.py        read length stats
mrnalen.py        mRNA length stats
```

`preliminaryA.py` looks for a long A or T run followed by the adapter, reverse-complements poly(T) hits so everything ends up in the same orientation, and keeps the ~100 nt of transcript sequence before the tail. Reads are labeled `keep`, `both`, `neither`, or `short` depending on what was found.

`blastA.py` does the same job a different way: it builds a BLAST database from the reads and searches it with hook sequences (a short A/T run plus adapter prefix) instead of a regex. The goal is to compare both approaches on the same data and see which one holds up better once things scale.

`draft/` holds earlier scripts kept for history, not in active use.

### notebooks/

`qcfastq.ipynb` has the read-length QC and the parameter checks behind `preliminaryA.py`, including confirming the adapter shows up in both orientations and testing how much of the adapter is actually needed.

### envs/

`env1.yml` is the conda environment for this repo.

### shell/

Scripts for running extraction across many FASTQ files at once.

### dummy_3end.json

A placeholder HMM structure. Not the real model yet, just a sketch of the states it should eventually have.

## Environment setup

Two conda environments are used in this repo, kept separate so BLAST
(an older package) doesn't force version conflicts with the analysis stack.

### Analysis environment (notebooks, stats scripts)

```bash
conda env create -f envs/env1.yml
conda activate 3end
```

### BLAST environment (blastA.py)

```bash
conda env create -f envs/blast-legacy.yml
conda activate blast
```

Register the Jupyter kernel (only needed once, using the `3end` env):

```bash
python -m ipykernel install --user --name 3end --display-name "3end"
```

Open a notebook in VS Code, select the `3end` kernel, and check you're using
the right Python:

```python
import sys
print(sys.executable)
```

It should point inside the `3end` conda environment.

## blastA.py notes

`blastA.py` builds a BLAST database from the reads (`formatdb`) and
searches it with poly(A)/poly(T) hook sequences (`data/hooks.fa`, built by
`hookprep.py`) using `blastall -p blastn`.

Getting a working, trustworthy search took three rounds of debugging:

**DUST filtering.** BLAST filters out low-complexity regions from the
query by default. Our hooks are mostly a homopolymer run (15 nt of A or T
out of a 35 nt query), so the default filter was masking out the exact
part of the hook we care about, returning zero hits regardless of
e-value. Fixed with `-F F`.

**Scoring scheme.** `blastA.py` started out reusing a scoring scheme from
a BLAST script in another project (`-r 1 -q -1 -G 2 -E 1`), tuned for
long sequence-vs-sequence alignments. Applied to a 35 nt query, that
scheme is too weak to produce a significant e-value even for a
near-perfect match. Dropped the custom scoring in favor of BLAST's
defaults, which is correct for a short, near-exact query like this.

**Strand search.** `blastn` searches both strands of the query by
default. Since `polyA_hook` and `polyT_hook` are already
orientation-specific (one is the reverse complement of the other),
leaving both strands on meant each hook was also implicitly searching
for the other hook's pattern, so most hits were double-counted under
both hooks (502 hits but only 250 unique reads). Fixed with `-S 1`
(plus strand only): 501 hits, 498 unique reads.

Current working command (what `blastA.py` runs under the hood):

```bash
blastall -p blastn -d build/reads.fa -i data/hooks.fa -F F -S 1 -e 1e-10 -m 8
```

### First result (1k.fastq.gz)

- 501 hits total, 498 unique reads with at least one hit
- 2 reads hit by both hooks (genuinely ambiguous orientation), one of
  which matches a read already flagged by manual inspection during the
  regex/notebook work as having both a PolyA and PolyT junction
  (`c3e3d120-3869-4a45-98fa-7eb281b5ed2b`), a useful cross-check between
  the two methods
- comparison against `preliminaryA.py` (regex-based extraction) is a
  planned next step, not done yet
